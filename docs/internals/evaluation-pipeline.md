# Evaluation Pipeline

A CEL expression moves through configuration, parsing, checking, planning, and evaluation. Keeping
those stages separate explains both the error model and why compiled programs should be reused.

## Pipeline at a glance

| Stage | Main result | Work performed |
| --- | --- | --- |
| Configure | `ScriptCompiler` or `Env` | Select declarations, types, libraries, macros, regex engine, and evaluation options |
| Parse | Parsed `Ast` | Parse source, expand macros, and record source information |
| Check | Checked `Ast` | Resolve names and overloads and attach type and reference metadata |
| Plan | `Script` or `Program` | Build a reusable executable tree and apply eligible planning-time optimizations |
| Evaluate | CEL result plus per-call details | Resolve input variables, execute the plan, and preserve CEL value/error/unknown semantics |
| Convert | Requested Java-facing result | Apply the high-level result contract or expose the low-level `Val` |

Most applications use `ScriptCompiler`, which performs the parse, check, and plan stages when
`compile` is called. Advanced integrations can perform them separately with `Env`.

## 1. Configure

Configuration establishes the language visible to the expression:

- variable, function, and type declarations;
- the container used for qualified-name resolution;
- standard and custom macros;
- type adapters and providers;
- libraries and overload implementations;
- program options such as constant optimization, state tracking, or partial evaluation.

A `ScriptCompiler` is immutable after it is built and snapshots its builder inputs. An `Env` is
mutable during configuration, but its checker-related configuration freezes on the first check.
Configure an environment completely before sharing or checking with it.

## 2. Parse

Parsing turns source text into an expression tree and source information. Configured macros are
expanded during this stage, so the expression tree can contain generated subexpressions that map
back to the original source.

Syntax and macro-expansion issues belong to this stage. A parsed AST is not necessarily checked and
therefore does not yet carry resolved overload or type information.

## 3. Check

Checking resolves identifiers, fields, functions, and overloads against the configured environment.
It attaches:

- a type map keyed by expression ID; and
- a reference map containing resolved names and overload identifiers.

This metadata is authoritative for later planning. It lets the planner distinguish, for example, an
exact standard overload from a custom function with a similar source shape.

`Env.compile` performs parsing followed by checking. Callers using the lower-level methods should
inspect the returned issues before using the AST.

## 4. Plan

Program construction translates the AST into a reusable `Interpretable` tree. A checked AST enables
typed planning, including eligible native specializations. Configured `OptOptimize` independently
folds eligible constant shapes. An unchecked AST is accepted by the low-level API but uses the
established planning path because the type and reference maps are absent.

Planning applies configured program options and installs the adapter, provider, overload
dispatcher, regex engine, and any default bindings. The result is an interpreter plan, not
generated Java, generated bytecode, or machine code. Each evaluation creates or accepts its
call-specific activation.

Options that need established evaluator behavior—such as state tracking, exhaustive evaluation,
partial evaluation, or custom decorators—select that path. Unsupported expression shapes also
retain established interpreter nodes. See [native evaluation](native-evaluation.md).

## 5. Evaluate

Each call supplies an activation, commonly through a map from variable names to Java values. Default
variables, when configured, form a parent activation and call-specific variables take precedence.
The reusable plan then evaluates against that activation.

The caller retains ownership of the activation and all reachable input values. Do not mutate them
while evaluation is running. A program may be evaluated concurrently when its configured custom
components and the caller's input ownership are also safe for concurrent use.

Low-level `Program.eval` returns:

- the result as a CEL `Val`; and
- distinct per-evaluation details and mutable evaluation state.

The state is empty during ordinary evaluation. Tracking options populate it with intermediate
values; exhaustive evaluation additionally disables normal short-circuit behavior.

## 6. Interpret the result

CEL errors are values in the low-level evaluator, not unexpected Java failures. Unknowns are also
CEL values and are distinct from errors, absent fields, and Java `null`. The high-level `Script`
API converts a CEL error to `ScriptExecutionException`; an unknown can only be returned through
result forms that can represent a general CEL value or object.

Unexpected internal Java failures are exceptions. Host integrations should not treat them as CEL
error values.

See [errors, unknowns, and partial state](../concepts/errors-unknowns-and-partial-state.md) for the
full distinction.

## Reuse boundary

Parsing, checking, and planning are normally one-time work for a source/configuration pair.
Evaluation is the repeated, input-specific operation. Reusing a `ScriptCompiler` and the resulting
`Script`, or reusing a low-level `Program`, avoids rebuilding that pipeline for every request.

This reuse boundary also matters for optimizations such as constant folding and literal-regex
compilation: their setup cost is paid while constructing the program, while their prepared form can
be used by later evaluations.
